# data-store

A Rust crate that uses DataFusion to read gnomAD browser data from Parquet files.

This README is a working draft while the crate takes shape.

## Requirements

Tool versions are pinned in the repo root `.tool-versions`.

## Build and test

Run these from `data-store/`, or use the `make` targets from the repo root.

```bash
cargo build
cargo test
```

The same checks CI runs (formatting, clippy, Rust tests, `index.d.ts` freshness, Node tests):

```bash
make validate-data-store   # from the repo root
make fix-data-store        # apply formatting and clippy fixes, regenerate index.d.ts
```

The tests read only the small Parquet files in `tests/fixtures/`. They show the code works
against that shape of data, not that it works against a real export. Use the example below
for that.

## Node bindings

The crate also builds as a Node addon through NAPI-RS, loaded from `bindings/index.js`. Install
the Node dependencies first (from `data-store/`; pnpm finds the workspace root itself):

```bash
pnpm install --filter @gnomad/data-store...
```

Build the addon and run its tests:

```bash
pnpm build:native          # debug build; writes bindings/ and refreshes index.d.ts
pnpm build:native:release  # release build; use this for timing anything
pnpm test:node             # loads the built addon, so rebuild after any change under src/
```

`index.d.ts` is generated by the build and committed; CI fails if it is out of date.

## Expected Parquet layout

Readers take a root directory containing one subdirectory per dataset:

```
<DATA_ROOT>
└── clinvar_variants_grch38
    ├── chrom=1/*.parquet
    └── chrom=2/*.parquet
```

The `chrom=` directory names are read as the `chrom` column, and queries filter on it to skip
other chromosomes' files; the files themselves need no chromosome column.

`tests/fixtures/` follows this layout. A full copy of the data lives at
`gs://gnomad-v4-data-pipeline/output/parquet/demo-mirror/2026-11-02`; with the right
permissions, copy its `parquet` directory to your machine to use as `<DATA_ROOT>`.

## Run the example against a Parquet directory

```bash
cargo run --release --example read_clinvar_variant -- <DATA_ROOT> 1-66926-AG-A
cargo run --release --example read_clinvar_region -- <DATA_ROOT> 1 926026 1477343
```

Against the fixtures:

```bash
cargo run --example read_clinvar_variant -- tests/fixtures 1-66926-AG-A
```

## Run a local graphql-api on Parquet (experimental)

The API can serve GRCh38 ClinVar variants (single variants and regions) from this crate instead of
Elasticsearch.

1. Build the bindings in release mode:

   ```bash
   pnpm build:native:release
   ```

2. Start the API without Elasticsearch, Redis or GCP access (from `data-store/`):

   ```bash
   cd ../graphql-api
   PARQUET_DATA_STORE_ENABLED=true \
   PARQUET_ONLY=true \
   PARQUET_DATA_ROOT=<DATA_ROOT> \
   ./start.sh
   ```

   | Variable                     | Effect                                                                                  |
   | ---------------------------- | --------------------------------------------------------------------------------------- |
   | `PARQUET_DATA_STORE_ENABLED` | Load the addon and route supported queries to it. Without it the API behaves as before. |
   | `PARQUET_ONLY`               | Never contact Elasticsearch; skips the IP whitelist load. Requires the flag above.      |
   | `PARQUET_DATA_ROOT`          | Parquet root directory. Required when the store is enabled.                             |

   `PARQUET_ONLY` refuses to start if `REDIS_HOST`, `JSON_CACHE_ENABLE_ALL` or `JSON_CACHE_LARGE_GENES`
   is set. To use Parquet alongside a real Elasticsearch cluster, leave out `PARQUET_ONLY` and set the
   usual `ELASTICSEARCH_URL`.

   Browser pages that show ClinVar data also request `meta { clinvar_release_date }`, which is still read
   from Elasticsearch. The field is non-null, so in `PARQUET_ONLY` mode its error discards the whole
   response: those pages fail, and only direct API queries such as the one below work.

3. Query it (GraphiQL is also served at <http://localhost:8010/api>):

   ```bash
   curl -s localhost:8010/api -H 'Content-Type: application/json' -d '{
     "query": "{ clinvar_variant(variant_id: \"1-66926-AG-A\", reference_genome: GRCh38) { variant_id clinical_significance } }"
   }'
   ```

Only GRCh38 ClinVar single variants and regions are served from Parquet so far. In `PARQUET_ONLY` mode every other query
returns an error saying it isn't supported by the Parquet client yet.
